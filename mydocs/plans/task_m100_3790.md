## 1. 문제

현재 `CI`는 review-only fast-pass와 단일 `frontend_required`만 구분한다. 따라서 Studio 단축키나
명령 정책처럼 Rust·WASM·렌더 출력과 무관한 변경도 Rust lint, test archive, 8개 shard, Native Skia와
Canvas, Rust/Python CodeQL까지 실행한다. Rust 검증의 결함 검출력은 유지하되 관련 없는 변경에서만
worker를 생략하려면 frontend 여부가 아닌 독립 영향축이 필요하다.

## 2. 목표 출력

classifier는 다음 값을 하나의 판정으로 만든다.

| 출력 | 값 | 의미 |
| --- | --- | --- |
| `rust_required` | `true|false` | Rust lint·default test 필요 여부 |
| `frontend_mode` | `none|unit|package` | Studio 전역 typecheck·단위 gate 또는 전체 package gate 범위 |
| `render_required` | `true|false` | Canvas visual diff와 CanvasKit readiness를 포함한 Render Diff 필요 여부 |
| `native_skia_required` | `true|false` | Native Skia 검증 필요 여부 |
| `codeql_languages` | 언어 CSV 또는 `none` | JavaScript/TypeScript·Python·Rust 분석 범위 |
| `classification_status` | `classified|full` | 정상 분류 또는 fail-closed 전체 검증 |
| `classifier_version` | 정수 문자열 | 판정 규칙 버전 |
| `reason` | 안정된 reason 목록 | 실행 기록과 회귀 분석 근거 |

## 3. 안전 경계

- 첫 PR은 shadow 판정과 summary만 추가한다. 기존 `frontend_required`와 모든 worker `if` 조건은 유지한다.
- classifier·workflow·Cargo 변경, `src/main.rs`, rename, 빈 파일 목록, API 오류, PR 3,000개 및 push
  300개 경계, 미분류 경로는 `classification_status=full`로 닫는다.
- rename은 현재 경로와 이전 경로를 모두 평가하되 Stage 1에서는 전체 검증 판정으로 고정한다.
- pull request merge ref에서 실행한 classifier는 advisory로만 취급한다. 실제 skip 활성화 전에는 base의
  신뢰된 classifier를 실행하거나 같은 수준의 보호 경계를 마련한다.
- review-only fast-pass와 required check 이름 `Build & Test`의 의미는 바꾸지 않는다.
- `src/main.rs`는 #3789에서 render/export 진입점이 모듈화되기 전까지 render 포함 full로 처리한다.
- `frontend_mode=unit`도 `rhwp-studio/tsconfig.json`의 전체 `src`를 대상으로 하는 `tsc --noEmit`과
  전체 Studio unit test를 실행한다. `package`는 이 계약에 Vite·extension·package build를 추가한다.
- 현재 Render Diff workflow는 좁은 Canvas visual diff와 Studio 앱 전체를 띄우는 CanvasKit readiness를
  함께 실행한다. 활성화 전에는 두 gate의 영향축을 분리하거나 실제 의존 경로의 보수적 합집합을
  `render_required`로 확정한다. 경로·파일명 heuristic만으로 skip하지 않는다.

## 4. 단계와 조정된 실행 순서

1. **Stage 1 — shadow classifier와 fixture**: #3785, #3656, #3670, #3672, #3690의 실제 파일
   목록을 fixture로 고정하고 판정만 기록한다.
2. **Stage 2 — shadow 관찰**: PR별 예상 worker와 실제 worker 결과를 대조하고 false negative가 없음을
   확인한다.
3. **Stage 3 — frontend 축 활성화**: `unit`, `package`, `render`를 분리하고 aggregate에서
   `success|skipped` 진리표를 검증한다.
4. **Stage 4 — Rust·Native Skia 조건화**: Rust 비영향 PR에서 Rust worker를, render 비영향 Rust PR에서
   Native Skia를 생략한다.
5. **cache 회귀 확인**: #3684를 완료한 #3810의 정리 후 기준선 4.73GB와 Stage 4 이후 cache 총량을
   대조한다. 기준선 회귀가 없으면 별도 대기 없이 다음 단계로 진행한다.
6. **Stage 5 — CodeQL 언어 분리**: 고정된 4.73GB 기준선 회귀 여부를 확인하며 workflow별 언어 축을
   활성화한다.
7. **Stage 6 — artifact retry**: shard count artifact의 primary/retry 중 하나 이상을 aggregate에서
   인정한다.
8. **Stage 7 — draft 경량화**: draft에는 영향별 경량 검증을 수행하고 `ready_for_review`에서 최종 검증을
   보장한다.

각 활성화 단계는 별도 PR로 진행한다. Stage 1 merge 전에는 skip을 활성화하지 않고, Stage 2 관찰 자료가
충분하지 않으면 다음 단계로 넘어가지 않는다.

## 5. Stage 1 범위

- `CI preflight`의 shadow output과 Job Summary 기록

- 계획·단계 보고서·오늘할일 기록

## 6. Stage 1 비범위

- #3789의 `src/main.rs` 모듈 분리 구현
