# 수행계획서 — #3888 CI slow shard 분리와 일반 7-shard 재분배

- 이슈: [#3888](https://github.com/edwardkim/rhwp/issues/3888)
- 기준 브랜치: `upstream/devel` `85d334728`
- 작업 브랜치: `task/3888-ci-slow-shard`
- 실측 기준: PR #3741 CI run `30810987621`

## 문제

현재 default-feature 테스트는 `hash:m/8`로 8개 worker에 나뉜다. 실행 건수는 602~651건으로
가깝지만 shard 3은 `overflow_cell_lines_do_not_grow`(133.510초), HWP5 전수
roundtrip(52.407초), 대형 HWP5 roundtrip(29.499초)이 함께 배치되어 nextest Summary가
168.457초였다. 다른 shard는 10.331~55.550초였다.

## 구현 계획

1. 기존 `test-shard` 단일 matrix를 유지하고 worker 수를 8개로 고정한다.
2. matrix에 `slow shard` 1개와 `shard 1/7`~`shard 7/7`을 명시적으로 선언한다. 단일 matrix를
   유지해 `fail-fast: true`가 여덟 worker 전체에 적용되게 한다.
3. `cargo metadata --no-deps`의 test-enabled target을 slow + 일반 7개 archive에 독점 배정한다.
   전체 `cargo nextest list`를 선행하지 않으므로 plan 단계가 모든 target을 먼저 compile하지 않는다.
4. slow worker는 `overflow_cell_baseline` target만 담은 archive를 단독 실행한다. 이 target에는
   실행 test가 하나뿐이므로 regular archive 중복과 runtime filterset 제외가 필요하지 않다.
5. build job은 A/B matrix 두 runner로 나뉘어 자기 target selector만 compile하고, slow + 일반 7개의
   artifact를 upload한다. 일반 archive는 각각 63~64 target을 담고, builder는 source bytes를 균형화한다.
   각 worker는 자기 artifact 하나만 download한다. builder는 archive별 실제 runnable count를 남기고,
   `Build & Test`는 여덟 expected count와 여덟 실행 count의 합계를 대조한다.

## 수용 기준

- `Default-feature tests (slow shard)`와 `Default-feature tests (shard 1/7)`~`(shard 7/7)`이
  같은 `test-shard` matrix에서 시작한다.
- 일반 worker archive에는 slow target이 없고 slow worker archive에는 해당 target만 있다.
- worker는 full test archive가 아니라 자기 `archive_label`의 artifact 하나만 download한다.
- expected count와 실행 count artifact는 각각 정확히 8개이며 합계가 일치한다.
- workflow 구문 및 target selector 분할 계약을 로컬에서 검증하고, PR 최신 head의 GitHub Actions에서
  전체 CI 성공을 확인한다.

## 위험과 완화

- target 단위 배정은 test-name hash보다 실행 건수 편차가 커질 수 있다. 변경 PR의 실제 shard Summary
  시간을 기록해 예상보다 긴 일반 shard가 새로 생기지 않았는지 확인한다.
- A/B builder는 공통 library·dependency를 각 runner에서 중복 compile할 수 있다. build 시간과 source
  bytes를 함께 기록해 병렬화 이득이 중복 비용보다 큰지 확인한다.
- 단일 133초 테스트는 더 쪼개지지 않으므로 완전한 시간 균등화는 불가능하다. 전용 worker로
  임계 경로를 현재 168초에서 약 133초로 줄이는 것이 이번 범위다.

## 로컬 검증 결과

| 항목 | 결과 |
| --- | --- |
| `actionlint .github/workflows/ci.yml` | 통과 (v1.7.12) |
| worker run shell 추출 후 `bash -n` | 통과 |
| matrix·target selector 정적 계약 | 통과: slow target 1개, regular target 442개, archive label 8개, target 중복·누락 없음 |
| `git diff --check` | 통과 |

제품 Rust·TypeScript·fixture는 바꾸지 않았다. 따라서 `overflow_cell_baseline`을 포함한 Cargo 제품
테스트는 이 workflow 변경의 로컬 게이트에서 의도적으로 실행하지 않았다. 실제 nextest archive,
target selector별 실행 수, artifact 합계와 shard별 Summary 시간은 변경 PR의 최신 GitHub Actions로 확인한다.

## CI 피드백 보정

PR #3892의 첫 CI에서 slow worker는 `overflow_cell_lines_do_not_grow` 1건을 244.761초에 통과했다.
그러나 기존 Summary 파서가 복수형 `tests run`만 찾았고 nextest는 단일 실행에 `1 test run`을 출력해
`run` 값이 비어 종료 코드 1이 됐다. 실행 테스트 실패가 아니라 집계용 파서 결함이므로, 정규식을
`tests? run`으로 넓혀 단·복수형 모두를 수용한다.

보정 후 `1 test run`과 `650 tests run` representative Summary를 각각 `1`, `650`으로 파싱했고,
`actionlint`, worker shell `bash -n`, 당시 matrix/filterset 정적 계약, `git diff --check`도 다시 통과했다.

## Artifact 전송 병목 보정

첫 실행의 full archive는 1,350,230,657 bytes였고, slow worker의 artifact download만 165초가
걸렸다. 모든 worker가 같은 full archive를 받는 구조는 test 실행을 나눠도 network 병목을 줄이지
못한다. stage 3에서는 nextest archive의 binary 단위 선택 제약에 맞춰 runnable test 수 기반
binary-affine 7-shard allocator를 도입했다.

3단계에서는 worker별 archive download를 줄였지만, 단일 builder가 모든 target을 compile하는 구조는
남았다. 이 결과는 stage 3 기록으로 보존하고, 현재 구현의 정합 기준은 아래 두 builder runner 보정이다.

## 두 builder runner 보정

PR #3892 run `30816897723`에서 전체 test binary build는 7분 27초였고, 그 뒤의 archive 생성과
upload는 약 41초였다. 두 번째 GitHub-hosted runner가 archive 생성만 맡으면 빌드 산출물을 artifact로
다시 전달해야 하므로 이득이 없다. 대신 기본 member `rhwp`의 440 integration test target과 lib/bin
target을 Cargo selector 단위로 둘로 나눠, 두 builder가 서로 다른 test target만 컴파일하도록 보정한다.

planner는 `cargo metadata --no-deps`만 읽으므로 전체 test build를 선행하지 않는다. builder A/B는 각자
선택 target의 archive를 만들고, 같은 selector의 nextest list에서 runnable count를 기록한다. 집계는
expected count와 worker run count를 archive label별로 합산해 coverage 검증을 유지한다. 상세 계획은
[`task_m100_3888_stage4.md`](../working/task_m100_3888_stage4.md)에 기록한다.
